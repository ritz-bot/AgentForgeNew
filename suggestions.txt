Multi AI Agent: interview presentation and improvement notes

1. What this project actually is

This repository is best described as a configurable AI-agent application with a lightweight full-stack setup:

- `Streamlit` frontend for user input
- `FastAPI` backend for request handling
- `LangGraph` ReAct agent layer
- `Groq` LLM integration through `ChatGroq`
- optional live web search through `Tavily`
- Docker + Jenkins + SonarQube + AWS ECR/ECS deployment pipeline

Important interview positioning:
- Present it as a "configurable AI agent platform" or "foundation for multi-agent systems"
- Do not oversell it as a true orchestrated multi-agent system, because the current code creates one agent per request rather than coordinating multiple specialized agents

2. Best 2-minute presentation flow

Use this flow in the interview:

"This project solves a common LLM problem: models are good at reasoning, but they may not have current information. I built a configurable AI-agent application where the user can define the agent role through a system prompt, choose the model, and decide whether live web search is allowed.

On the frontend, I used Streamlit to keep the interaction simple. The UI captures the system prompt, model selection, web-search toggle, and user question. That request is sent to a FastAPI backend.

On the backend, I validate the selected model and pass the request to the agent layer. In the core agent module, I instantiate a Groq model and conditionally attach the Tavily search tool. I then use LangGraph's ReAct agent pattern so the model can decide whether to call the search tool before answering.

From an engineering perspective, I also packaged the app with Docker and added a Jenkins pipeline that runs SonarQube analysis, builds the container, pushes it to AWS ECR, and deploys it to ECS Fargate. So the project is not only an AI demo, it also shows production-minded delivery." 

3. Architecture story to explain clearly

Frontend:
- `app/frontend/ui.py`
- collects `system_prompt`, `model_name`, `allow_search`, and the user query
- sends a POST request to `/chat`

Backend:
- `app/backend/api.py`
- validates model selection
- invokes the agent core
- returns the final generated answer

Agent layer:
- `app/core/ai_agent.py`
- builds `ChatGroq(model=...)`
- conditionally adds `TavilySearchResults`
- creates a ReAct-style agent using `create_react_agent`

Launcher:
- `app/main.py`
- starts FastAPI in the background and then launches Streamlit

Infra:
- `Dockerfile`
- `Jenkinsfile`
- `custom_jenkins/Dockerfile`

4. Demo flow to use in the interview

Use one example with search off and one with search on.

Demo 1: role-based behavior
- system prompt: "You are a concise medical assistant who explains in simple terms."
- ask a stable question such as "What are the early symptoms of anemia?"
- explain that the system prompt changes agent behavior without changing code

Demo 2: search-enabled behavior
- system prompt: "You are a market research assistant. Cite recent developments clearly."
- enable web search
- ask a current-events style question
- explain that Tavily is attached only when the search toggle is enabled

5. Strong points you can claim confidently

- Clear separation of concerns between UI, API, core logic, config, and common utilities
- Dynamic agent behavior through user-provided system prompts
- Tool-augmented LLM design with optional web search
- Production-oriented packaging with Docker and CI/CD
- Logging and custom exception handling

6. Things you should say carefully

If asked "Is this really multi-agent?"
- Best answer: "Right now it is a configurable single-agent implementation with a structure that can be extended into a true multi-agent system. The next step would be adding specialized agents such as researcher, planner, and critic with routing between them."

If asked "Why Streamlit and FastAPI together?"
- Best answer: "Streamlit made the demo layer fast to build, while FastAPI keeps the agent logic behind an API boundary so the frontend can be replaced later without changing the core logic."

If asked "Why LangGraph?"
- Best answer: "LangGraph gives me an agent-oriented abstraction and a good path to extend this from a single tool-using agent into a more explicit workflow or multi-agent graph later."

7. Biggest weaknesses in the current repo

The codebase works as a demo, but it has several gaps that a strong interviewer may notice:

- no README, architecture diagram, or setup instructions
- no automated tests
- large blocks of old commented-out code are still present in core files
- dependencies are not cleanly managed
- container build currently risks copying sensitive and unnecessary files
- backend startup is development-oriented rather than production-oriented
- frontend and backend are tightly coupled through a hardcoded local URL

8. Highest-priority improvements

Priority 1: security and packaging
- Add a `.dockerignore` file immediately
- Exclude `.env`, `venv/`, `logs/`, `__pycache__/`, and `*.egg-info/`
- Reason: the current Dockerfile does `COPY . .`, so without `.dockerignore` you risk shipping secrets and local artifacts into the image

Priority 2: clean the repo
- Remove the large triple-quoted old code from:
  - `app/main.py`
  - `app/backend/api.py`
  - `app/core/ai_agent.py`
- Remove generated files from versioned source structure where possible
- Reason: this makes the project look unfinished and weakens maintainability

Priority 3: fix dependency management
- Add missing `requests` to `requirements.txt`
- Remove duplicate `streamlit`
- Pin dependency versions
- Consider replacing `setup.py`-only packaging with `pyproject.toml`

Priority 4: improve runtime robustness
- Validate `GROQ_API_KEY` and `TAVILY_API_KEY` at startup
- Replace `time.sleep(2)` backend wait with a real health-check/retry loop
- Do not run Uvicorn with `--reload` in production mode
- Add request timeouts for frontend-to-backend calls

Priority 5: improve API and error handling
- Do not return internal file names and line numbers to the client on failures
- Return clean API errors with user-safe messages
- Add explicit request/response schemas and examples

Priority 6: make it a stronger "multi-agent" story
- Add at least two specialized agents, for example:
  - Research agent: gathers live information
  - Answer agent: synthesizes and formats the response
- Optional third agent:
  - Critic agent: checks factual consistency and prompt adherence
- Add routing logic so this becomes an actual multi-agent workflow

Priority 7: improve DevOps credibility
- Add a test stage to Jenkins before build/deploy
- Add SonarQube quality-gate enforcement
- Tag images with commit SHA instead of only `latest`
- Add a health check endpoint
- Consider separate frontend and backend containers for cleaner deployment

9. Specific code-level observations you should be ready to discuss

- `app/main.py` starts FastAPI in a thread and Streamlit in the foreground. This is fine for a demo, but it is not the cleanest production process model.
- `app/frontend/ui.py` uses a hardcoded API URL: `http://127.0.0.1:9999/chat`
- `app/config/settings.py` stores the allowed model names in code; that is okay for a demo but would be better as environment-driven config
- `requirements.txt` contains duplicate `streamlit` and does not explicitly list `requests`
- `Jenkinsfile` handles scan/build/deploy, which is good, but it does not currently run tests or block deployment on quality-gate failure

10. Best "next version" roadmap to mention

If the interviewer asks what you would do next, say this:

"My next iteration would focus on four areas: first, make the repo production-clean with README, tests, config validation, and better dependency management; second, split frontend and backend deployment cleanly; third, add observability and health checks; and fourth, convert the current single-agent flow into a real multi-agent workflow with specialist agents and routing logic."

11. If you have very little time in the interview

Say this in one line:

"This is a tool-augmented AI-agent application where Streamlit handles the user workflow, FastAPI exposes the agent service, LangGraph and Groq drive the reasoning, Tavily provides optional live search, and Jenkins plus Docker plus AWS turn it into a deployable system."
